O Modelo Mental Mínimo Viável

Conceitos · 2 min de leitura
Git vs. GitHub — a diferença em uma linha:
Git é a ferramenta instalada no seu computador que rastreia mudanças no código. GitHub é um site na nuvem onde você armazena e compartilha esse histórico com seu time. Git sem GitHub funciona; GitHub sem Git não.

Todo arquivo no Git vive em um dos 4 lugares abaixo. Entender esse fluxo resolve 90% das dúvidas do dia a dia:

✏️
Lugar 1
Working Directory
Seus arquivos no disco. Você edita aqui.
git add
→
🎯
Lugar 2
Staging Area
Rascunho do próximo commit. Você escolhe o que entra.
git commit
→
📦
Lugar 3
Local Repository
Histórico salvo no seu PC. Ainda só seu.
git push
→
☁️
Lugar 4
GitHub (Remote)
Histórico na nuvem. Visível para o time.
Fluxo reverso: Use git pull para trazer atualizações do GitHub para o seu Working Directory em um único comando (equivale a git fetch + git merge).

Os 20% dos Comandos Essenciais

O Guia de Sobrevivência
⚙️ Configuração Inicial — rode uma vez na vida
git config
Define seu nome e e-mail — essa identidade aparece em todos os commits.
$ git config --global user.name "Seu Nome" $ git config --global user.email "seu@email.com" $ git config --list # confirma o que foi salvo
🚀 Início e Clonagem — só no começo do projeto
git init
Cria um repositório Git do zero na pasta atual.
$ git init # Initialized empty Git repository in ./meu-projeto/.git/
git clone
Baixa um repositório completo do GitHub (histórico incluído) para o seu PC.
$ git clone https://github.com/usuario/repositorio.git $ cd repositorio # entra na pasta criada
🔄 Ciclo de Salvamento Diário — você vai rodar isso todo dia
git status
Mostra o estado atual — quais arquivos mudaram, quais estão na staging.
$ git status # On branch main # Changes not staged for commit: # modified: src/app.js
git add
Move arquivos do Working Directory para a Staging Area (prepara para o commit).
$ git add src/app.js # adiciona um arquivo específico $ git add . # adiciona TUDO que mudou (use com cuidado)
git commit
Cria um snapshot permanente dos arquivos em staging, com uma mensagem descritiva.
$ git commit -m "feat: adiciona validação de CPF no formulário" # [main a3f2c1d] feat: adiciona validação de CPF no formulário
git push
Envia seus commits locais para o GitHub, tornando-os visíveis para o time.
$ git push origin main # envia branch "main" para o remote "origin" $ git push origin feature/login # envia outra branch
git pull
Baixa e integra as atualizações do GitHub na sua branch atual — rode sempre antes de começar o dia.
$ git pull origin main # Already up to date. ← ou lista os arquivos atualizados
🌿 Ramificação e União — trabalhar em paralelo sem conflitos
git branch
Lista todas as branches locais — a com * é a que você está agora.
$ git branch # * main # feature/login # bugfix/header
git switch
Muda para outra branch ou cria uma nova (-c) — substituto moderno do checkout.
$ git switch main # muda para branch existente $ git switch -c feature/login # cria E já muda para a nova branch
git merge
Integra os commits de outra branch na branch em que você está atualmente.
$ git switch main $ git merge feature/login # traz feature/login → main

Fluxo de Trabalho de uma Empresa Real

Git Flow Simplificado
A regra de ouro: Nunca commite direto na main. Todo trabalho novo vive em uma branch própria e entra via Pull Request.
1
🌅 Comece o dia sincronizado

Garanta que sua main local está idêntica ao GitHub antes de qualquer coisa.

$ git switch main $ git pull origin main
2
🌿 Crie uma branch para a tarefa

Use um nome descritivo — geralmente o ID da tarefa + descrição curta.

$ git switch -c feature/AUTH-42-login-google
3
💻 Desenvolva e faça commits frequentes

Commits pequenos e descritivos são mais fáceis de revisar e de reverter se necessário.

# ... você edita arquivos ... $ git add . $ git commit -m "feat(auth): integra SDK do Google OAuth" # ... mais código ... $ git commit -m "test(auth): adiciona testes de login Google"
4
☁️ Suba a branch para o GitHub

O -u conecta sua branch local à remota — após isso, basta usar git push.

$ git push -u origin feature/AUTH-42-login-google
5
🔍 Abra um Pull Request (PR) no GitHub

Após o push, o GitHub exibe um botão Compare & pull request. Clique, escreva uma descrição clara do que foi feito e solicite review de um colega. O PR é onde o time discute o código.

6
💬 Responda o review e ajuste

Se o reviewer pedir mudanças, edite o código, faça um novo commit e dê push na mesma branch — o PR se atualiza automaticamente.

# ... ajusta o código conforme feedback ... $ git add . $ git commit -m "fix(auth): corrige escopo de permissões do Google" $ git push
7
✅ Merge aprovado — integre à main

Com aprovação, clique Merge pull request no GitHub. Sua branch entra na main. Opcionalmente delete a branch de feature — o histórico permanece.

# Após merge via GitHub, atualize seu local: $ git switch main $ git pull origin main

Socorro, Deu Ruim!

Gestão de Crise
💣 Situação 1: Comitei algo errado (ainda não fiz push)
O commit existe apenas no seu PC — você tem total liberdade para desfazê-lo sem afetar ninguém.
  • 1
    Desfaz o commit mas mantém as alterações no código: o flag --soft volta os arquivos para a staging (prontos para um novo commit).
    $ git reset --soft HEAD~1
  • 2
    Alternativa — descarta TUDO do commit (cuidado!): --hard apaga o commit E as alterações no código permanentemente.
    $ git reset --hard HEAD~1 # ⚠️ irreversível
  • 3
    Só quer corrigir a mensagem do commit? Use --amend — reescreve apenas o último commit.
    $ git commit --amend -m "mensagem corrigida"
⚔️ Situação 2: Conflito de Merge — o Git não sabe qual código usar
Ocorre quando você e um colega editaram a mesma linha do mesmo arquivo. Parece assustador, mas o processo é simples.
  • 1
    Git anuncia o conflito: rode git status para ver quais arquivos estão em conflito (marcados como both modified).
    $ git merge feature/login # CONFLICT (content): Merge conflict in src/auth.js # Automatic merge failed; fix conflicts and then commit the result.
  • 2
    Abra o arquivo conflitante. O Git inseriu marcadores visuais mostrando os dois lados:
    <<<<<<< HEAD ← seu código (branch atual) const titulo = "Meu Projeto"; ======= ← separador const titulo = "Nosso Projeto"; ← código do colega >>>>>>> feature/login ← branch de origem
  • 3
    Edite manualmente deixando apenas o código final correto. Apague os marcadores (<<<<<<<, =======, >>>>>>>) — eles não devem ir para o commit.
    const titulo = "Nosso Projeto"; ← resultado final (você decidiu)
  • 4
    Marque como resolvido e finalize:
    $ git add src/auth.js $ git commit -m "merge: resolve conflito em auth.js"
Dica profissional: VS Code e outros editores modernos exibem botões visuais — Accept Current Change, Accept Incoming Change, Accept Both — diretamente sobre os conflitos. Use-os para resolver conflitos mais rápido sem precisar editar o texto manualmente.
